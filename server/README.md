# API администрирования

Бэкенд панели `/panel`: кейсы и статьи блога в PostgreSQL, вход по почте и
паролю, публикация снапшота на сайт. Архитектура и причины решений — в
[../docs/backend.md](../docs/backend.md).

Сайт остаётся статическим экспортом. База — источник правды для редактирования,
`content/cases.json` и `content/blog.json` — снапшоты, которые уезжают в
репозиторий при публикации и из которых собирается статика. Поэтому кейсы и
статьи по-прежнему предрендерены в HTML, а падение API не роняет сайт.

## Запуск локально

Нужен Docker (Docker Desktop на Windows) и Node 22+.

```bash
cd server
cp .env.example .env      # значения по умолчанию годятся для локальной работы
docker compose up -d db   # поднять только PostgreSQL

npm install
npx prisma migrate deploy             # накатить готовую миграцию (таблицы)
npm run seed                          # перенести content/cases.json и content/blog.json в базу
npm run user:create -- you@example.com owner   # пароль спросит интерактивно
npm run dev                           # API на http://localhost:4000
```

Затем в корне проекта:

```bash
# .env.local
NEXT_PUBLIC_ADMIN_API_URL=http://localhost:4000
```

и `npm run dev` — `/panel` откроется с формой входа вместо поля для токена.

Весь стенд целиком (API в контейнере) — `docker compose up`. Учтите, что без
аргумента compose ещё и пересобирает образ API — это несколько минут. Для
обычной разработки хватает `docker compose up -d db`, а API запускается через
`npm run dev`.

Для CRM (`../crm`) в `.env` нужен её origin, иначе браузер не пропустит запросы
с кукой:

```
WEB_ORIGIN=http://localhost:3000,http://localhost:5173
```

> `server/.env` подключается флагом `--env-file-if-exists` в npm-скрипте `dev`.
> Сам по себе файл не читается: Prisma грузит его только ради `DATABASE_URL`,
> поэтому раньше все остальные переменные молча оставались на значениях по
> умолчанию. Если добавите новый способ запуска — не забудьте флаг, иначе
> `WEB_ORIGIN`, `COOKIE_*` и лимиты из файла не подействуют.

## Проверка

```bash
curl http://localhost:4000/health          # {"ok":true}
curl http://localhost:4000/cases/snapshot  # то, что уедет в content/cases.json
```

## Публикация

`POST /cases/publish` собирает снапшот и коммитит его вместе с новыми картинками
в репозиторий сайта, GitHub Actions пересобирает статику и заливает её по FTP.

Без `GITHUB_TOKEN` публикация работает «вхолостую»: снапшот собирается и
валидируется, но никуда не отправляется — так и задумано для локальной работы.

Токену нужны права `Contents: read and write` на один репозиторий сайта. Он живёт
только в `server/.env` и в браузер не попадает — в этом главное отличие от режима
без бэкенда.

## Маршруты

| Метод | Путь                          | Кто может                   |
| ----- | ----------------------------- | --------------------------- |
| POST  | `/auth/login`                 | все (лимит 10/5 мин)        |
| POST  | `/auth/logout`                | все                         |
| GET   | `/auth/me`                    | все                         |
| GET   | `/cases`                      | вошедшие                    |
| PUT   | `/cases`                      | вошедшие                    |
| POST  | `/cases/:caseId/assets/:slot` | вошедшие                    |
| POST  | `/cases/publish`              | вошедшие                    |
| GET   | `/cases/snapshot`             | все (только опубликованные) |
| GET   | `/health`                     | все                         |

`PUT /cases` заменяет список целиком и требует `version` — ту, что вернул
`GET /cases`. Если контент успели изменить в другом окне, придёт `409`, и правки
не затрут чужие.

## Развёртывание на VPS

Пошаговый чеклист — [../docs/deploy.md](../docs/deploy.md). Конфигурация готова:
`docker-compose.prod.yml` (Caddy с автосертификатом → API → Postgres, наружу
торчат только 80 и 443), `Caddyfile`, `.env.production.example`,
`scripts/setup-server.sh` (Docker + файрвол на чистой Ubuntu),
`scripts/backup.sh` (pg_dump с ротацией).

## Что важно при переезде на сервер

- `COOKIE_SECURE=true` и HTTPS — иначе сессионная кука уйдёт открытым текстом.
- `WEB_ORIGIN` — точные адреса сайта и CRM через запятую: с `credentials`
  браузер не примет `*`.
- `COOKIE_DOMAIN` — если API живёт на поддомене (`api.it-optimization.ru`).
- Бэкапы `pg_dump` по расписанию и проверка, что дамп восстанавливается.
- Картинки лежат в томе `uploads` — его тоже надо бэкапить до первой публикации.

## Пароли и доступ

Пароли хранятся как Argon2id, минимальная длина — 12 символов. Сессии серверные:
в куку уходит случайный секрет, в базу — только его SHA-256, поэтому доступ
отзывается мгновенно (`revokedAt`), а дамп базы не даёт войти. Смена пароля через
`npm run user:create` закрывает все открытые сессии пользователя.
