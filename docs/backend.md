# Бэкенд: целевая архитектура и подготовка

Документ описывает архитектуру бэкенда и причины принятых решений.

**Статус: бэкенд развёрнут и работает.** Код — в [`server/`](../server)
(Fastify + Prisma + PostgreSQL), боевой экземпляр — на VPS за
`https://api.it-optimization.ru`: HTTPS от Let's Encrypt, вход по почте и
паролю, 16 кейсов в базе, ежедневные бэкапы. Развёртывание описано в
[deploy.md](deploy.md), локальный запуск — в [server/README.md](../server/README.md).

Переключение между режимами — одна переменная окружения
`NEXT_PUBLIC_ADMIN_API_URL`: задана — панель ходит в API с логином и паролем,
не задана — коммитит в репозиторий по токену.

---

## 1. Почему не «просто подключить базу»

Сайт — статический экспорт (`output: "export"`), у него нет рантайма: ни API
routes, ни server actions, ни соединения с БД. PostgreSQL требует процесса,
который будет к ней подключаться. Значит появление базы — это всегда появление
**отдельно живущего сервиса**, и главный вопрос не «какая БД», а **где крутится
API и что становится источником правды для публичных страниц**.

Отсюда две развилки, и их стоит развести во времени.

---

## 2. Целевая архитектура

```
┌──────────────┐        ┌──────────────────────┐        ┌──────────────┐
│  /panel      │ HTTPS  │  API (Node)          │        │  PostgreSQL  │
│  (браузер)   │──────▶ │  /auth  /cases       │──────▶ │  cases,      │
│              │ cookie │  Prisma              │        │  users, ...  │
└──────────────┘        └──────────┬───────────┘        └──────────────┘
                                   │
                                   │ публикация
                                   ▼
                        ┌──────────────────────┐
                        │  Пересборка сайта    │
                        │  (CI или сборщик     │
                        │   на том же сервере) │
                        └──────────┬───────────┘
                                   ▼
                            статика на хостинге
```

Ключевое решение: **публичный сайт остаётся предрендеренным**. База — источник
правды для редактирования, статика — снапшот для посетителей. Так кейсы остаются
в HTML (SEO не страдает), а падение API никогда не роняет сайт.

Альтернатива — перевести сайт на SSR/ISR на том же сервере и читать кейсы из БД
на лету. Тогда публикация мгновенная и пересборка не нужна, но сайт перестаёт
быть статикой и переезжает с shared-хостинга на VPS целиком. Это допустимый
финал, но менять и хранилище, и модель рендеринга одним шагом — плохая идея.
Порядок: сначала база и API, потом (если понадобится) SSR.

### Где это крутится

| Компонент  | Рекомендация                                                    |
| ---------- | --------------------------------------------------------------- |
| API + БД   | VPS (reg.ru / Timeweb / Selectel), 1–2 ГБ RAM, Docker Compose   |
| PostgreSQL | Контейнер рядом с API либо managed-инстанс у того же провайдера |
| Картинки   | Диск сервера или S3-совместимое хранилище; в БД — только пути   |
| Сайт       | Как сейчас: статика на хостинге reg.ru                          |

Отдельная managed-БД (Neon, Supabase) удобна, но это внешний сервис за пределами
РФ — для коммерческого сайта российской компании лучше держать данные у
российского провайдера.

### Стек API

Fastify + Prisma + TypeScript. Prisma даёт типы прямо из схемы, а типы кейса на
фронте и в базе становятся одним контрактом. NestJS — если захочется жёсткой
структуры под рост; для CRUD одной сущности он избыточен.

## 3. Схема PostgreSQL

Полная схема — `server/prisma/schema.prisma`, миграция — в
`server/prisma/migrations/`. Это рабочая конфигурация: именно она накатана на
боевую базу.

Основное:

**`cases`** — портфолио. `id` (uuid) — вечный идентификатор, `slug` — то, что
сейчас называется `key`: участвует в URL, в именах файлов и в ссылках со страниц
услуг, поэтому меняется отдельно от `id`. `position` — порядок на сайте (сейчас
это порядок массива в JSON). `status` — `draft` / `published`, чтобы готовить
кейс, не показывая его. `tags` — массив строк (`text[]`), а не одна строка.

**`case_assets`** — картинки кейса: слот (`cover` / `detail` / `detail_mobile`),
путь, размеры, хэш содержимого, размер файла. Отдельная таблица нужна, потому что
у ассета своя жизнь: он может пережить смену slug и должен уметь чиститься.

**`posts`** — статьи блога. Появилась вместе с редактированием блога из панели:
раньше статья жила в двух местах сразу — метаданные в константе `BLOG_POSTS`,
текст в каталоге `messages/ru.json`, — и править её из панели было нельзя, а
каталог с телом всех статей грузился на каждой публичной странице. Форма
повторяет `cases`: `slug`, `status`, `position`, даты, мягкое удаление. Тело
статьи (`sections`) лежит в `jsonb` одним массивом `[{ heading, body: string[] }]`
— разделы никогда не читаются отдельно от статьи, не ищутся и не
переиспользуются, поэтому отдельные таблицы дали бы только джойны. Обложка —
одна колонка `cover`, без таблицы ассетов: картинка у статьи ровно одна.
`services` — ключи услуг, о которых статья; связь двусторонняя и живёт здесь, а
не двумя картами в константах, иначе списки «услуга → статьи» и «статья →
услуги» рано или поздно разъезжаются.

**`users`** — вход в панель: `email`, `password_hash` (Argon2id или bcrypt),
`role`. Пароли никогда не хранятся и не логируются в открытом виде.

**`sessions`** — серверные сессии: в cookie уходит только случайный
идентификатор, в базе лежит его хэш, срок жизни и отпечаток клиента. Серверные
сессии выбраны вместо JWT, потому что их можно мгновенно отозвать.

**`audit_log`** — кто, что и когда изменил, с diff в `jsonb`. На одном
администраторе избыточно, но стоит копейки и однажды ответит на вопрос «когда
пропал этот кейс».

**`leads`** — заготовка под будущие формы. Сейчас заявки идут в мессенджеры мимо
сайта; когда появится форма, ей понадобится ровно эта таблица. В схеме она есть,
чтобы решение принималось осознанно, а не в спешке.

## 4. Контракт API

Панель уже говорит с абстракцией `CasesApi` (`src/lib/admin/cases-api.ts`), а не
с GitHub напрямую. Будущая HTTP-реализация закрывает тот же интерфейс:

```
POST   /auth/login      { email, password }        → Set-Cookie (httpOnly, Secure, SameSite=Lax)
POST   /auth/logout                                → 204
GET    /auth/me                                    → { id, email, role }

GET    /cases                                      → { cases: Case[], version }
PUT    /cases           { cases: Case[], version } → { version }   // порядок + правки разом
POST   /cases/assets    multipart                  → { path, hash, width, height }
POST   /cases/publish                              → { buildId }   // запуск пересборки

GET    /posts                                      → { posts: Post[], version }
PUT    /posts           { posts: Post[], version } → { version }   // порядок + правки разом
POST   /posts/:id/cover multipart                  → { cover, version }
POST   /posts/publish                              → { commitUrl, buildUrl }
```

У блога свой счётчик ревизий (`content_revisions.scope = "posts"`): разделы
панели не пересекаются ни одним полем, и общий счётчик отклонял бы правку кейса
только потому, что рядом сохранили статью.

`version` — тот же механизм оптимистичной блокировки, что и сейчас: панель
присылает версию, на которой открылась, сервер отклоняет запись, если данные
успели измениться. Сегодня это SHA коммита, завтра — `updated_at` или счётчик
ревизий. Логика панели при этом не меняется.

Обязательное на стороне API: rate limit на `/auth/login`, ограничение размера
загрузки, пере-кодирование картинок на сервере (доверять типу файла из браузера
нельзя), CORS только на домен сайта.

## 5. Что уже сделано ради этого перехода

| Шов                                 | Где                           | Что даёт                                                    |
| ----------------------------------- | ----------------------------- | ----------------------------------------------------------- |
| Кейсы — данные, а не код            | `content/cases.json`          | Строка таблицы 1:1, сид переносится скриптом                |
| Модель совпадает с будущей таблицей | `id`, `slug`, `tags[]`, даты  | Миграция без изменения формы данных                         |
| Чтение спрятано за репозиторием     | `src/lib/cases/repository.ts` | Замена JSON → Prisma в одном файле                          |
| Страницы получают кейсы пропсами    | server components             | Данные приходят сверху; источник может стать асинхронным    |
| Запись спрятана за `CasesApi`       | `src/lib/admin/cases-api.ts`  | Замена GitHub → HTTP в одном файле, интерфейс панели тот же |
| Блог устроен теми же швами          | `content/blog.json`, `BlogApi` | Статья — данные; те же два режима записи, тот же снапшот    |
| Оптимистичная блокировка по версии  | `load()` / `publish()`        | Тот же контракт, что у будущего API                         |

---

## 6. Что сделано и что осталось

Сделано:

1. **Швы.** Чтение за `CaseRepository`, запись за `CasesApi`, страницы получают
   кейсы пропсами.
2. **Схема и сид.** `server/prisma/schema.prisma`, `npm run seed` переносит
   `content/cases.json` в таблицы.
3. **Auth.** `users` + `sessions`, Argon2id, httpOnly-кука, лимит на попытки входа.
4. **CRUD и картинки.** Замена списка целиком с проверкой версии, загрузка с
   пере-кодированием через sharp.
5. **Публикация.** Снапшот уезжает в репозиторий одним коммитом, дальше
   существующий деплой.
6. **Панель.** `HttpCasesApi` и форма входа; режим выбирается переменной окружения.
7. **Блог.** Статьи переехали из `messages/ru.json` в `content/blog.json` и в
   таблицу `posts`; в панели появился раздел «Блог» — создание, правка,
   порядок, обложки. Оба режима записи (`githubBlogApi` / `httpBlogApi`)
   закрывают один интерфейс `BlogApi`.

Осталось (нужен сервер):

8. **Инфраструктура.** VPS, `docker compose up`, домен `api.it-optimization.ru`,
   сертификат, бэкапы `pg_dump` по расписанию.
9. **Боевые переменные.** `COOKIE_SECURE=true`, `WEB_ORIGIN`, `GITHUB_TOKEN`.
10. **Переключить сайт.** Прописать `NEXT_PUBLIC_ADMIN_API_URL` и пересобрать.

Ничего из этого не трогает публичные страницы: для посетителя сайт не меняется.
